# Architecture

This describes the intended design. Details marked **verify** are assumptions about platform or library behaviour that must be checked against current docs before building on them. If one turns out wrong, update this file. Details marked **verified** were checked against the Electron 44 documentation on 2026-10-13; details marked **untested** follow the docs but have not yet been confirmed on a real machine.

## Processes

| Part | Runs in | Responsibility |
| --- | --- | --- |
| Main | Electron main | Global shortcut, windows, permissions, capture orchestration, ffmpeg, storage, analysis jobs, API key, local bridge server |
| Overlay | One transparent renderer per display | Region selection, context panel, recording outline and timer |
| Recorder | Hidden renderer in its own session | Records one display with `getDisplayMedia` and `MediaRecorder`, streams the bytes to main |
| Library | Main app window renderer | Browse, search, review, refine, rename, import, settings |
| Chrome extension (deferred) | The user's Chrome: a service worker, an in-page overlay, an offscreen document | Screenshots and records part of a tab without leaving it; sends the capture to main over the capture bridge |
| Recreation frame | Sandboxed iframe or webview inside Library | Renders AI-generated code, nothing else |
| MCP server | Separate Node entry point, stdio | Read-only access to the library folder for AI tools. Works whether or not the app is running |
| Figma plugin | Figma (later phase) | Lists and inserts assets via the local bridge server |

The app lives in the menu bar and keeps running with the library window closed, so the shortcut always works. While the main window is open it is a regular app, so it shows in Cmd+Tab; macOS only lists regular apps there, and they always have a Dock icon, so the Dock icon shows during that time too. When the window closes it goes back to menu bar only (`main/appSwitcher.ts`). Overlays and the hidden recorder never change this.

gil's mark is the Dot cloud (2026-11-24, from the menu bar icon mockups): a turning ball of points whose flares are stray points flying out. Its drawing and the status mapping live in `shared/dotCloud.ts`. The menu bar icon turns once every 18 s at 12 frames a second and shows what gil is doing: idle is a quiet ball, capturing (selecting through saving) adds a ring, analyzing makes the flares pop in and out, and ready (10 s after the last queued analysis finishes) holds the flares out. Main has no canvas, so a hidden, sandboxed window with no preload draws each frame at 1x and 2x (`main/trayIcon.ts`); frames are template images (macOS colours them for a light or dark menu bar) and are kept once drawn. The app icon `build/icon.png` is drawn from the same code by `pnpm exec electron scripts/make-icon.mjs`: light points on a dark rounded square, flares out, the mark about 630 px across so it has the same breathing room as Burr's and Peri's icons.

Suggested layout:

```
src/
  main/         shortcut, windows, capture, ffmpeg, analysis, storage, bridge
  preload/      typed IPC surface
  overlay/      selection and recording UI
  recorder/     hidden page that records a display
  library/      main app UI
  extension/    Chrome extension (built separately into out/extension)
  shared/       zod schemas, types, pure logic (geometry, slugs, frame selection)
  mcp/          standalone MCP server
figma-plugin/   later phase
```

`shared/` must not import Electron, so the MCP server and tests can use it. Preload scripts run sandboxed and can only require `electron`, so each must bundle to a single file: they import channel names from the per-window `shared/*Channel.ts` files and nothing else at runtime. `pnpm build` fails if a preload gains a shared chunk or another import.

## Capture pipeline

1. **Shortcut.** `globalShortcut` in main. On trigger, show the overlay window on every display. The overlays are created hidden at launch and already showing the selection UI, so the shortcut only has to show them.
2. **Overlay window.** Frameless, transparent, always on top (`screen-saver` level), covering one display, above full-screen apps. It is created with `type: 'panel'`, which makes it a non-activating panel: it takes the mouse and keyboard without making gil the active app, so the app being captured stays frontmost (**verified** in the docs, **untested**).

   Keeping gil's UI out of recordings does not rely on `setContentProtection(true)`. **Verified:** that call sets `NSWindowSharingNone`, which ScreenCaptureKit-based capture ignores after an intentional macOS change. Electron patches its own capturer to leave out its own protected windows, but only those protected before the stream starts, and this is not documented behaviour. Normally this does not matter, because gil records the target window on its own (step 5) and a window recording never contains other windows. For the display fallback, content protection stays on as a first line of defence and two rules do the real work: the dimming is confirmed off screen before recording starts, and during recording nothing is drawn inside the selected region. The outline and timer sit just outside it, where the crop removes them.
3. **Selection and target window.** The user drags over part of a window. When selection starts, main fetches the on-screen window list (front to back, with global bounds, owner app and title) from `CGWindowListCopyWindowInfo`, called through `osascript -l JavaScript`; this needs no native module and no Automation permission, and takes about 100 ms (**tested** from a shell). Titles are only readable with Screen Recording permission. When the drag ends, the renderer reports the rectangle in CSS pixels relative to its own overlay window; main converts it to global CSS pixels and picks the frontmost ordinary window (layer 0, visible, not gil's own) under the selection's centre (`shared/windowList.ts`). The selection is clipped to that window and stored relative to its top-left corner. The overlay outlines the window and names it before the user presses Record. If no window is under the selection (the desktop), the target is the display instead.

   The region is later converted to physical pixels using the size of the recorded frames rather than a nominal scale factor, because the two can differ (scaled display modes, a window on a display with a different scale). All geometry conversion lives in pure, tested modules (`shared/geometry.ts`, `shared/windowList.ts`); mixed-DPI multi-monitor setups are where this breaks.
4. **Context.** Optional text from the panel, stored with the capture.
5. **Recording.** Record the whole target window, then crop afterwards with ffmpeg. This is simpler and more reliable than cropping a live stream. Because the window is recorded on its own rather than the screen, the user can cover it, switch apps or open other windows while it records, and the clip still shows only that window (**untested**: this is how macOS window capture works, but it has not been tried with this app; a minimized window, or one on another Space, may stop updating). Switching tabs inside the recorded window changes what is recorded. For the display fallback, the whole display is recorded instead.

   **No built-in browser.** gil had its own browser tab until 0.5; it was removed on 2026-11-16 so that all capture goes through the overlay and every asset type is read from pixels (the Chrome extension, a later phase, is the route for exact values from web pages).

   A **Chrome extension** could do the same for tabs in the user's own Chrome; a first version is described under "Chrome extension and capture bridge (deferred)" below.

   **Verified** capture path: the hidden recorder page calls `navigator.mediaDevices.getDisplayMedia()`, and `setDisplayMediaRequestHandler` on the recorder's own session answers with the source main chose: the `desktopCapturer` window source whose id is `window:<CGWindowID>:…`, or the screen source whose `display_id` matches. `getDisplayMedia` needs a user gesture, so main starts it with `executeJavaScript(…, true)`. It asks for `cursor: 'never'` so the mouse pointer is left out of recordings (**untested**: Chromium ignores the constraint where it cannot honour it). `MediaRecorder` prefers H.264 and streams chunks to main, which appends them to a temp file outside the library. That file is uncropped and is always deleted after the crop. The crop assumes the recorded frames cover the window's frame exactly (no shadow margin, **untested**) and that the window is not resized while recording.

   While recording, the overlay ignores mouse events (`setIgnoreMouseEvents(true, { forward: true })`, **verified** for macOS) so the user can interact with the content underneath. Mouse moves are still forwarded, which lets the timer turn the window interactive again while the pointer is over it. The overlay also gives up keyboard focus when recording starts.

   macOS may show a recurring prompt that the app is "requesting to bypass the system private window picker", because gil captures a window or display directly instead of using Apple's picker. The picker cannot be combined with a custom region overlay, so this is accepted.
   **Screenshots.** The panel's Screenshot button skips the recorder. Main hides the overlays and grabs one full-resolution still of the same target: the `desktopCapturer` thumbnail of the window or screen source, requested at the source's own pixel size (**untested**: the thumbnail is documented to fit within the requested size, so it should come back at full resolution). The crop is the same mapping as for a recording, measured against the image's real size, without the even-size rule video needs. For a display, main waits a moment after hiding the overlays so the dimming is gone; window grabs never contain gil's windows.
6. **Stop.** Shortcut again, click on the timer, or the maximum duration (default 10 s).
7. **Post-process.** ffmpeg crops to the region and writes `capture/clip.mp4` and `capture/poster.png` (a screenshot writes only the cropped `poster.png`) into a hidden staging folder inside the library, which is then renamed to the asset's name in one step. The asset is in the library straight away (the window refreshes if it is open, but is never opened or brought forward), with status `stored` until analysis exists (Phase 2), after which new captures start as `analyzing`. Before analysis suggests a name, a capture is named `capture-YYYYMMDD-HHMMSS`.
   **Nothing moved.** Right after a recording is saved, gil measures its motion (see Measured motion); if nothing moved, a notification says so straight away (a hover that was never triggered is the usual cause). The capture is still saved.
8. **Source metadata.** The target window's app name and title come from the window list, so they are recorded for every window capture. The URL is `null` (the Chrome extension, a later phase, will record it), and display captures have no source. Best effort; never block a capture on it.

### Chrome extension and capture bridge

Wired up on 2026-11-16 (**untested** in Chrome): main starts the bridge at launch, Settings → Chrome extension shows the extension folder (`out/extension` from `pnpm build`, or `Contents/Resources/extension` in the packaged app, copied there as `extraResources`) and copies the pairing code, and saved clips are analyzed like captures.

**Page styles.** When the user clips, the overlay reads the computed styles of what is inside the selection (`src/extension/pageStyles.ts`): for each text run that intersects it (at most 3,000 read), its font-family list, size, line height, weight, letter spacing and colour, with a few words of the text; and the background and border colours of the topmost painted elements on a 10×10 grid of points. Identical styles are merged (at most 40 text styles and 40 colours, `shared/pageStyles.ts`), sent in the capture metadata (the bridge allows headers up to 128 KB). It also reads, for elements at least half inside the selection, each one's box (`getBoundingClientRect`, relative to the clip), border radius and padding (at most 40, largest first, only elements that paint something or hold text), running animations from `document.getAnimations()` (duration, delay, easing, iterations, keyframes in short) and declared transitions from computed style (at most 30), and saved as `capture/page-styles.json`. Analysis gives them to the model as exact values to mark measured. Values only: no code, no font files.

The extension (`src/extension`, Manifest V3, built by `scripts/build-extension.mjs` into `out/extension` as one self-contained script per entry, loaded unpacked) captures from inside Chrome:

1. **Invoke.** Clicking the toolbar icon or pressing its shortcut (`Alt+Shift+G`, Chrome's `_execute_action`) grants `activeTab` for that tab. The service worker injects `overlay.js` with `chrome.scripting`. With no pairing code saved, it opens the options page instead.
2. **Select.** The overlay runs in the extension's isolated world inside a closed shadow root, with styles from a constructed stylesheet (not subject to the page's CSP). It reports the selection in viewport CSS pixels with the viewport size and `devicePixelRatio`. It ignores untrusted (script-generated) clicks, and stops key events in the panel from reaching the page's own handlers.
3. **Screenshot.** The overlay removes itself and waits two frames, then the service worker calls `chrome.tabs.captureVisibleTab` (PNG of the visible viewport).
4. **Record.** The overlay draws only an outline and timer outside the region (as gil's overlay does). The service worker gets a tab stream id with `chrome.tabCapture.getMediaStreamId({ targetTabId })`, which the `activeTab` grant allows (**untested**), and hands it to an offscreen document (`USER_MEDIA`), the only extension context that can hold a stream. That document records with `MediaRecorder`, asking for the viewport's exact pixel size and falling back to any size up to it. A captured tab keeps rendering when the user switches to another tab or app (**untested** for this extension; documented behaviour of tab capture). Recording stops on the icon, the shortcut, the in-page timer, after 10 s, or when the tab navigates (the stream ends and what was recorded is kept). Closing the tab discards it.
5. **Send.** The whole viewport image or video goes to gil with metadata (selection, viewport, real frame size, duration, context, tab URL and title). The offscreen document uploads recordings itself because they are too large for extension messaging. gil crops with the same mapping as every other capture (`rectToVideoCrop`, viewport as the source size), saves through the same code, and deletes the upload. The library updates without coming to the front. The in-page overlay shows a short "Saved to gil as …" or the error, then removes itself.

**Capture bridge.** An HTTP server in main on `127.0.0.1:47823` (`src/main/bridge.ts`), started at launch. `GET /v1/ping` checks pairing; `POST /v1/captures` takes the image or video as the body and the metadata as base64 UTF-8 JSON in `X-gil-Capture`, validated with zod (`shared/bridge.ts`). Every request must have a `Host` of the loopback address and port (defeats DNS rebinding), an `Origin` of `chrome-extension://…` (web pages can reach 127.0.0.1 but not with that origin), and `Authorization: Bearer <pairing code>` (`bridgeRequest.ts`, unit tested). The pairing code is random, created on first launch, kept in `userData/bridge-token`, shown in the library's Chrome Extension panel, and pasted once into the extension's options page. Uploads are capped at 256 MB and written to a temp file outside the library. If the port is taken, the panel says so. Native messaging was not used: Chrome would start a second copy of the app as the host, and host-to-extension messages are capped at 1 MB.

The extension's requests to the loopback address rely on its host permission for `http://127.0.0.1/*`, which exempts it from CORS (**untested**: Chrome's Private Network Access rules are expected not to apply to extensions).

### Packaging

`pnpm package` uses electron-builder (`electron-builder.yml`) to make `dist/mac-arm64/gil.app`: `LSUIElement` so it starts without a Dock icon (see appSwitcher.ts for when it gets one), and ffmpeg unpacked from the asar archive. It is ad-hoc signed (`identity: "-"`) with the hardened runtime off, which runs on the Mac that built it without a developer certificate. macOS ties privacy permissions to the code signature, so a rebuilt app may have to be granted Screen Recording and Documents access again (**untested**). Notarized distribution needs a Developer ID and is not set up.

### Publishing and updates

**Now: self-signed releases on Cloudflare R2** (decided 2026-10-27, until gil has an Apple Developer ID). macOS only installs an update signed with the same certificate as the installed app, and keeps privacy permissions only while the signature's identity stays the same, so every release is signed with one local certificate, `gil Self-Signed`, created once in the user's login keychain (Keychain Access → Certificate Assistant → Create a Certificate, Self Signed Root, Code Signing). `pnpm release` (`scripts/release.mjs`) refuses to run with uncommitted changes, an existing tag for the version, a missing certificate or no update address; otherwise it runs the checks, builds with `electron-builder.self.yml` (dmg and zip, no hardened runtime, not notarized, generic update provider pointing at `release.json`'s `updateUrl`), verifies the signature, uploads the zip, dmg and blockmaps to the R2 bucket with `wrangler` (signed in once with `npx wrangler login`, so no key passes through Claude), uploads a stable `gil.dmg` for first installs, uploads `latest-mac.yml` last, and tags and pushes `v<version>`. Because the app is not notarized, the first install needs right-click → Open; after that updates install themselves. The bucket is served from the user's own domain.

**Later: Developer ID.**

Decided 2026-10-23, postponed 2026-10-27 until the product settles. Started by hand, `.github/workflows/release.yml` runs on macOS: checks, build, then electron-builder with `electron-builder.release.yml`, which signs with the user's Developer ID certificate, uses the hardened runtime (`build/entitlements.mac.plist`), notarizes with Apple, and publishes a dmg (first installs) and a zip (what updates download). The workflow stops with a message until the secrets exist: `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`, and `RELEASES_TOKEN` for publishing. The user adds these in GitHub; they never pass through Claude.

**Versions.** gil uses semantic versioning in `package.json`, staying at 0.x until the first public release: the minor number goes up for a batch with new features, the patch number for a batch of fixes only. Every batch handed to the user gets a new version. A release is the tag `v<version>` on the commit it was built from, created by `pnpm release`. Each build also records the commit it came from (`-dirty` if built from uncommitted changes), injected at build time as `__GIL_COMMIT__`. The version and commit show at the top of the menu bar menu, in the library's footer and in the About panel, for example `0.2.0 (af5f4f2)`. electron-updater compares versions, so a release must always have a higher version than the one installed.

Installed release builds update the way a game patches (`main/updates.ts`, electron-updater): on launch, before anything else starts, gil checks the update server (giving up after 5 seconds). If a newer version exists, a small, non-closable "Updating gil" window shows download progress (an update already downloaded in the background is reused, so that is quick), then gil installs it and relaunches into the new version by itself. There is no skip; if the check, the download or its progress stalls (60 seconds without progress), gil starts as it is so it never locks the user out. While running, gil checks again after a minute and every six hours, downloads in the background, and offers "Restart to Update" in the menu bar; a downloaded update also installs on quit. Builds without `app-update.yml` (local `pnpm package`, `pnpm dev`) never check. When this path is switched on, its publish target should move to the same R2 bucket (`electron-builder.release.yml` still names a public `gil-releases` repository from before R2 was chosen).

### Permissions

macOS requires Screen Recording permission. **Verified:** `systemPreferences.getMediaAccessStatus('screen')` reports the status, but `askForMediaAccess` only covers camera and microphone, so there is no call that asks for it. Attempting a capture (`desktopCapturer.getSources`) is what makes macOS show its prompt and list the app in System Settings. When the status is not `granted`, the shortcut opens the library window, which explains why, triggers the prompt, deep-links to System Settings and offers a relaunch. Electron's docs do not mention a restart for screen access; that macOS applies the grant only to a freshly started app comes from third-party reports, so the relaunch step is there but **untested**. In development the permission attaches to the Electron binary or the terminal that started it, which is a common source of confusion; the README says what to do.

## Analysis pipeline

Runs in main as a queued background job, one asset at a time. Each step writes its output to the asset folder so a failed job can resume and so the user can see what the model saw.

The pipeline since 2026-11-23. the owner's aims: the exact recreation must match the capture, because it proves gil understood it, and the recipe built on it is what users reuse with their own content. Measure and trace first, for free; one model (`claude-opus-5-5`) plans, builds and corrects; gil checks on the Mac and stops the rounds as soon as the check passes. (A cheaper planner and fixer, tried on 2026-11-22/23, cost less but drew shapes wrong and varied from run to run.)

1. **Measure (no model).** Motion from every frame of the clip (segments, timing, easing, stagger, and when each movement was 10%, 20%… done); the exact colours of the poster; boxes cut from the pixels along empty gutters; and, for clips from the Chrome extension, the page's own values: fonts, sizes, colours, each element's box, radius and padding, running animations and declared transitions.
2. **Pick frames.** The resting state of each quiet stretch, the frame before and the last frame of each movement, and the rest of a 24-frame budget inside the movements at even steps of progress, so more frames land where the most changes. Frames are sent at three pixels per CSS pixel of the capture (long side between 640 and 1568 px): an image is billed by its area, and a capture recorded at two pixels per CSS pixel gains nothing from being enlarged further.
3. **Trace** (`shared/trace.ts`). A few resting frames and up to three in-between frames of each movement are split into their flat colours and each colour's outline is followed along the pixel edges, moved onto the true edge inside its soft (anti-aliased) pixels, and turned into clean SVG paths: real corners, straight lines and fitted curves (soft-edge colours that exist only as a rim are dropped; a frame needing too many points is skipped). The model gets exact outlines for letters, logos, marks and icons, and the real in-between shapes of a morph, instead of drawing them by eye.
3b. **Plan** (prompt `describe.md`, answered as JSON checked with zod, since the schema is too large for the API's constrained output). The model sees the frames and every measurement and writes the spec: what each thing is, which measured movement and box belongs to which element, states and triggers. Measured numbers are copied as facts; anything the measurements missed is listed in `caveats` as "Not measured: …" with an estimate.
3c. **Real fonts for text** (`main/analysis/textFonts.ts`, `shared/fontEmbed.ts`, built 2026-11-23, not yet run through a paid analysis). The plan lists each line of text that stays text (`texts`: the text, its box, weight, the typeface it looks like and up to eight free Google Fonts families). gil sets each line in those fonts (and the page's own font when the Chrome extension read it) in the hidden render window, keeps the closest by letter shape (lines with the same suggestions share one font), and from the ink boxes works out the font size, letter spacing and position that put the text exactly on the capture's. The build is given that CSS and writes `url(gil-font:<family>-<weight>-<style>)` as the font source; gil replaces it with the font file as a data: URL whenever the code is rendered or saved (from its font cache only: the key never causes a download and is never used as a path), and takes the data out again before the code goes to a model (Refine) or an AI tool (MCP). The traced outlines of matched text are left out of the build prompt. Small text takes the best match; larger text must match well or it stays traced, since it may be lettering no free font has. Only font downloads leave the Mac. `pnpm bench textfit` shows a fit over the capture.
3d. **Focus** (2026-11-23; the time span was run once through a paid analysis, the area and the review-screen field have not been). The user can say which part of a capture they want ("only the loading animation, not the photo", "just the button"): in the capture overlay's note, or afterwards under *What to recreate* in the review screen (`userContext`, read at the next analysis). The plan then describes only that part and answers where it is: a span of the clip (`focusFromMs`, `focusToMs`) and a box of the picture (`focusX`…`focusHeight`, fractions). gil cuts the capture to it with ffmpeg (`capture/focus.mp4`, its first frame `capture/focus.png`, the answer in `capture/focus.json`; `shared/motion.ts` `focusFrom`), measures that clip again from scratch (motion, frames, colours, boxes, traces), and the build, the local check, Refine and `check_use` all work on the cut-out part with its own size and length. The plan's numbers are a first reading; the measurements of the cut-out part are what the build is told to trust. If the cut fails, the whole capture is analyzed as before. A re-analysis with no focus removes the three files.
4. **Build** (prompt `recreate.md`). One self-contained `index.html` from the spec, the measurements and the frames, with every token and timing as a custom property on `:root`.
5. **Check and fix** (`main/analysis/check.ts`, `shared/patch.ts`). The recreation is rendered in the hidden sandboxed window and compared with the capture, with no model: placement and regions on up to six resting frames only (mid-movement, a timing difference inside the bar would look like a misplacement), timing (the recreation is played through at 30 fps and its movements measured like the capture's), and regions (where one has content and the other nothing, on a grid, so placeholder text for real text does not count). Shapes are compared too: at rest, each image's outlines (sharp brightness steps, at 3× CSS size) must have an outline within about two thirds of a CSS pixel in the other, for at least 93% of them both ways; that catches a mark or letterform drawn wrong, which the 2026-11-23 Mirego test showed the other checks miss. The bar is 2 px, 2 frames, nothing missing or extra, shapes lined up. Number gaps are patched in the code: every time-like custom property is scaled when all movements run too fast or slow by one factor, and the page is shifted when the whole thing sits a few pixels off; each patch is re-rendered and kept only if the check improves. In-between frames are checked for shape too, loosely (what the recreation draws must lie within 2 CSS px of an outline in the capture for 75% of it; the capture may also show page content behind). While something is still missing or wrong, up to two corrections (prompt `verify.md`): each gets at most ten frame pairs and the measured differences in words; each result is checked and patched the same way and kept only if the check says it is better. A model correction is only paid for when the check finds something it can act on (something missing or extra, shapes that do not line up, placement): a movement that merely starts or ends a little off is not, since the build already had the measured timings and what is left is usually the measurement itself (a pointer or the page moving in the capture). A correction that made nothing better is not followed by another.
6. **Recipe** (`shared/recipe.ts`). The build call also returns the recipe: parts by role with their slots, the steps in order with timings, how each effect is built for any content, how to adapt it, and what to keep. It is saved as `recipe.md` and served by the MCP server ahead of the spec and the code; the server's instructions and the Claude Code skill tell agents to build from it when the user asks for an asset with their own content. Reuse with the user's content is the point of gil (the owner, 2026-11-23); the exact recreation is the proof that the capture was understood.
7. **Save.** `spec.json`, `spec.md`, `recreation/index.html` and `base.html`, and `recreation/first.html`, the recreation as first made, which no Refine or edit ever overwrites. `asset.json` gets status `ready` and `analysis.usage`, priced per call at the model that answered, cached input included. Notify.

Refine is one round of the main model with the user's instruction (prompt `refine.md`), then the same local check and number patches; no second model round. Nothing is cached: each call's images differ, so a cache entry would cost its write premium and rarely be read. A correction call that fails keeps the build as it is.

Cost: measured on 2026-11-23 with the cheaper mix, $0.39 and $0.58 for two recordings with no correction and $1.00 with one; with one model throughout it is estimated at $0.60–0.80 with no correction and up to about $1.40 with two, not yet measured. `pnpm bench check <asset>` runs step 5 on a library asset with no API call.

The numbered list and component notes below describe the earlier pipeline (describe and recreate on one model, up to two model verify rounds); where they disagree with the above, the above is current.

### What is built (Phase 2)

- **Queue** (`main/analysis/queue.ts`): one asset at a time, keyed by asset id because analysis may rename the folder. New captures are queued automatically when an API key is saved; otherwise they stay `stored` and the library offers Analyze. Assets left `analyzing` when the app quit are requeued at launch. A finished or failed analysis posts a macOS notification. Token usage is logged to the console per asset; storing it per asset is Phase 3.
- **Frames** (`main/analysis/analyze.ts`, `shared/frames.ts`, `shared/ffmpegArgs.ts`): ffmpeg samples the clip at 20 fps into 64×64 grayscale thumbnails piped to stdout. Which of them count as moving comes from measured motion (below) when there is one; otherwise mean absolute difference between neighbours above 1.2 (of 255) counts as motion; pauses of four frames (200 ms) or fewer inside motion are merged into it. Selection keeps the middle of each quiet stretch, the frame before and the last frame of each active stretch, and spreads the rest of a 24-frame budget over the motion in proportion to its length, so morphs are seen through their intermediate shapes. The chosen frames are extracted as high-quality JPEGs, longest side capped at 1568 px, thinned evenly if together they pass 18 MB (the API allows 32 MB per request, and base64 adds a third), and written to `capture/frames/<ms>.jpg`. A screenshot is one frame, its `poster.png`. More frames cost more per analysis; the budget becomes a setting in Phase 4.
- **Measured motion** (`shared/motion.ts`, `main/analysis/analyze.ts`): for a recording where something moves, ffmpeg decodes the whole clip at 30 fps into 96×96 grayscale frames. Each frame step's change is measured per cell of an 8×8 grid, and the activity at that step is the mean of its most active cells (so a small element on a large page still registers). Stretches of activity (gaps up to 100 ms merged; single repeated frames filled in) become segments, each with start, end and duration (±1 frame), the box of cells that changed, a stagger when separate patches of change start at different times (with its direction), and an easing: the running total of activity is taken as progress over time and fitted with the closest CSS cubic-bezier (control points 0–1, coarse then fine search) plus the nearest keyword. When page content scrolls behind the captured thing (a fixed logo over a scrolling page), that scrolling would be measured as its motion. The clip is therefore also measured with scrolling left out, along each axis: each step's scroll is found as the shift that best explains it, a pixel counts as changed only if it differs both from where it was and from what scrolled into its place, and steps beside a found scroll where the page jumps faster than a frame can follow take the level of their neighbours. The plan is shown both measurements when they differ and answers `backdrop` (vertical, horizontal or none); everything after the plan uses the one it chose, and `motion.json` records the axis. Saved as `capture/motion.json` and given to every call as text, which tells the model to use these values and mark them measured. Limits: activity has no direction, so overshoot and springs are not measured; touching staggered items look like one patch; one segment can cover several elements. A small patch of change (two cells or fewer, the size of a mouse pointer) is left out when the clip also has larger motion, though a pointer moving fast across a wide, short capture can still be counted. A failure to measure never fails the analysis. Refine reuses the saved `motion.json`. When there is a measurement, the frames sent to the model are chosen from its segments instead of from whole-frame change (`differencesFromMotion`), so they land on the movements rather than on the pointer or noise.
- **Describe and recreate** (`main/analysis/claude.ts`, prompts in `main/analysis/prompts/`; superseded on 2026-11-22: planning now runs on `claude-haiku-5-5` without a server-side fallback, Refine caches the original frames, and a refusal fails the asset at once): both used `claude-opus-5-5` with adaptive thinking and `effort: "high"`, streamed, with structured output constrained to a zod schema (`shared/spec.ts`) through the SDK's `betaZodOutputFormat` and validated again. Server-side fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) lets the API retry on its default fallback model if the request is declined as a false positive; `analysis.model` records the model that actually answered. A refusal, an answer cut off at `max_tokens`, or one that does not validate is retried once and then fails the asset with a readable reason. Naming and tags come from the describe call rather than a separate cheaper model, since that is one fewer request per asset. No prompt caching yet: the two calls have different instructions ahead of the frames, so they share no cacheable prefix; it becomes worthwhile with refine (Phase 3).
- **Save**: `spec.json`, `spec.md` (generated from the spec), `recreation/index.html`, then asset.json (`ready`, title, kind, summary, tags, `analysis`). If the asset still has its capture-time name it is renamed to the suggested one, folder and `asset.json` together (`storage.renameAsset`); a name the user chose is never replaced.
- **API key** (`main/apiKey.ts`): typed once into the library's Settings, checked with Anthropic by looking up the model (no tokens used), then encrypted with `safeStorage` into `userData/anthropic-key.bin`. The renderer can set it, clear it and ask whether one exists; main never sends it back.
- **Font identification** (`main/fontIdentify.ts`, `main/fonts.ts`, `shared/fontCatalog.ts`, `shared/fontMatch.ts`, prompt `identify.md`; chosen 2026-11-16: Google Fonts, compared on the Mac): one model call reads the text, where it is (a box, so other text is left out), the weight and style, a guess at the typeface, and up to twelve free look-alikes by their Google Fonts names. gil downloads the catalogue (the Google Fonts families as listed by Fontsource, `api.fontsource.org`, no key) on first use and keeps it in `userData/fonts` for 30 days, then downloads each candidate's Latin WOFF2 from jsDelivr at the nearest weight (cached, at most 2 MB each; only those two hosts are fetched). Each candidate sets the same text in a hidden unprivileged window (`renderStill`, fonts as `data:` URLs); the capture's crop and each rendering are reduced to their ink (pixels far from the most common grey), cropped to it, scaled to 320×64 and compared by overlap. The result is a new `font` asset. `pnpm bench fonts <asset> "<text>" <weight> <families> [box]` runs the matching without a model call.
- **Lenses**: the overlay's picker (Auto, Motion, Component, Layout, Type, Colour) is saved as `asset.lens`. Analysis adds a lens note to every call (`LENS_NOTES` in `main/analysis/claude.ts`: layout asks for regions and a placeholder skeleton, type for every text level and a specimen, and so on) and the lens decides `kind`. The colour lens skips the model: the queue turns the capture into a colour system on the Mac (`applyColorLens`), so it works without an API key, and the capture's name becomes `colors`. The type lens makes one describe call only: gil builds the recreation itself as a type specimen from the spec's text levels (`shared/typeSpecimen.ts`: each level as a labelled sample line, its values as custom properties on `:root`), with no recreate or verify call. In the review screen, Another Lens… makes a new asset from the same capture: colour at once, the others queued for analysis (`duplicateForLens`).
- **Measured colours and the colour lens** (`shared/palette.ts`, `shared/colorSystem.ts`, `main/colorLens.ts`): the palette of an image is measured on the Mac by median cut over up to 120,000 sampled pixels, merged by perceived difference (ΔE under 6 in Lab), keeping colours over 0.4% of the image (`nativeImage.toBitmap()` is BGRA on macOS). Every analysis gives the model the poster's measured palette and asks it to use those exact values and mark them measured. The Colour Lens button in the review screen makes a separate colour system asset from any asset with an image, with no model call: measured colours, roles guessed from area, contrast and saturation (background, text, accents, neutrals), WCAG contrast pairs, and a swatch page as its recreation.
- **Import and notes** (`main/importImage.ts`, `main/libraryFiles.ts`): images dropped on the library grid, pasted (outside a text field), or picked with Import… become assets through the same path as a screenshot (`saveScreenshot` with `imported`). PNG and JPEG are decoded by `nativeImage`; WebP, GIF, HEIC, TIFF and BMP are first converted to PNG with macOS's `/usr/bin/sips` (EXIF orientation is not applied). A dropped or pasted file's path is read in the preload with `webUtils.getPathForFile` (items with no file on disk are skipped), and a pasted image with no file comes from Electron's asynchronous `clipboard.read()`. Main only imports absolute paths with an image extension. Notes cannot be saved while the asset is being analyzed, since analysis may rename its folder. With an API key they are analyzed like new captures. New Note creates a `note` asset whose text is `notes.md`; every asset's review screen has a Notes box that edits `notes.md`, and the MCP server serves it with the asset.
- **Search, glossary and export** (`shared/search.ts`, `shared/glossary.ts`, `main/libraryFiles.ts`): the library's search box filters with the same matching as the MCP server's `search_assets`. Settings → "Your terms" edits `glossary.json` in the library folder, which the MCP server's `get_glossary` serves. Export in the review screen copies the asset's whole folder into a folder the user picks (as `<name>`, or `<name>-2`… if taken).
- **Library actions** (`main/assets.ts`): rename to an exact name the user types (refused if taken or invalid; folder, `asset.json` and `spec.md` updated together), retitle, tags (normalized: trimmed, lowercase, unique, at most 20), and delete, which moves the folder to the macOS Trash with `shell.trashItem`. None of these run while the asset is being analyzed.
- **Editor** (`shared/edits.ts`, `library/Review.tsx`): the editable values are the custom properties parsed from the `:root` rules of `base.html`. Edits are compiled to one stylesheet: `:root` values, and per-element overrides marked `!important` under structural selectors. The preview shows unsaved edits by posting that stylesheet into the sandboxed frame, where the preview bridge (added by the recreation protocol, never saved) applies it after everything else, outside `<body>` so element positions in selectors do not shift. Click-to-select is also done by the bridge: it reports the clicked element's structural selector and computed styles, which the library validates with zod before using. Saving writes `edits.json` and rebuilds `index.html` from `base.html` (see ASSET_FORMAT.md). Generated code is shown in the outputs as text only.
- **Verify and correct** (`main/analysis/render.ts`, prompt `verify.md`): after the first recreation, gil renders it at the timestamps of the frames and sends Claude each original frame next to the recreation at the same moment, with the spec and the current HTML; Claude returns whether they match, the differences, and corrected HTML. Up to two rounds, stopping early on a match. Rendering uses a virtual clock injected before the recreation's scripts (`shared/recreation.ts`): timers, `requestAnimationFrame`, `performance.now` and `Date.now` run on a clock gil advances, and every CSS animation and transition is paused as it starts and then set to the requested moment, so each frame shows exactly that timestamp however slowly capture runs (**verified** on a real recreation in a test harness, outside the app). The hidden window is offscreen, sandboxed, with no preload, an in-memory session that cancels every request but the `data:` document, no permissions, no pop-ups or navigation, rendered at up to 4× and resized to the original frames' size. If the recreation cannot be rendered the check is skipped and the recreation kept. `analysis.rounds` counts the first recreation plus each verify round.
- **Refine**: the review screen's Refine box queues one round under `prompts/refine.md`, where the user's instruction wins over the original frames, then one verify round, against the frames saved in `capture/frames/` (re-extracted if missing). Every round is told the instructions already applied, kept in `recreation/refinements.json`, so a check against the original does not undo them; re-analyzing clears them. It replaces the recreation and its edits (the user is asked first when there are edits). A failed refinement keeps the previous recreation, leaves the asset `ready`, and records the reason in `analysis.error`.
- **Frame scale**: every frame sent to the model is scaled so its long edge is 1568 px, up or down. Small captures (a logo in a header) are scaled up, so the model sees their shapes in detail; the prompt states the scale so measurements stay in CSS pixels. Screenshots are scaled the same way.
- **Not built yet** (Phase 3): editable spec, per-asset token usage.

### Capture kinds beyond animation (2026-11-23)

- **Spacing and grid** (`shared/spacingSystem.ts`, `main/spacingLens.ts`): Another Lens… → Spacing and grid, free and on the Mac. Boxes come from the page through the Chrome extension, or are cut from the poster (`shared/layoutMeasure.ts`, which now also looks inside bordered or filled panels against their own background, and counts light panels as content). The spaces are the gaps between facing boxes and each box's insets inside the box that holds it; they are grouped into steps, snapped to the spacing values an earlier analysis named when within 1.5 px (pixels blur a space by about a pixel), and checked for a base unit. Equal boxes evenly spaced in a row are a column grid. `check_use` compares a draft's paddings, gaps and margins with the steps. Measured on the chat card: a 4 px unit, steps 20, 24, 26.
- **Effects, icons, page transitions, scroll**: lenses that shape the analysis (`LENS_NOTES` in `main/analysis/claude.ts`): effects get exact CSS values on a neutral shape over a matching backdrop; icons get the drawing rules (grid, stroke, joins, corners, fill) with numbers; transitions are described as what leaves, what is shared and travels, and what enters; scroll choreography is described against scroll progress, not time. For the Scroll lens gil also measures how far the page scrolled through the clip, from page content moving across the region (`shared/motion.ts` `scrollTimeline`), and gives the plan and build that timeline so effects can be placed against scroll position; it needs some page content to move, and is only as exact as that content is distinct. Effects and icons are not measured specially yet. Responsive behaviour (captures at several widths) was dropped on 2026-11-24.

### Measuring accuracy (benchmark)

The verify loop is Claude judging its own work, so accuracy is also measured outside the model.

- **Score** (`shared/score.ts`, `main/analysis/score.ts`): the recreation is rendered at the moment of each frame the model saw (`capture/frames/`), in the same hidden window as the verify step, resized to the frame, and compared with it. Both are scaled so the long edge is 256 px and compared with SSIM (structural similarity) per colour channel, with each 8×8 window weighted by how much is going on in it, so a matching empty background does not pad the score. 0–100 per frame; the asset's score is the mean over frames. No API calls. A recreation the user has refined or edited is scored against the original capture, so deliberate changes lower it.
- **Runner** (`main/bench.ts`, a second main-process entry built beside `index.js`, run with `pnpm bench`): `add <name>…` copies a library capture's `asset.json` and clip or screenshot into the benchmark, frozen from then on; `run` re-analyzes every benchmark capture in a throwaway library and reports score, cost and time for each next to the previous run; `score <name>…` scores library assets as they are and saves the frame pairs it compared; `list` shows the benchmark. It shows no windows, keeps its own settings folder (`~/Library/Application Support/gil-benchmark/`, with `captures/` and `runs/<time>/report.json` plus each run's recreations), so it can run while gil is open, and uses gil's saved API key, or `ANTHROPIC_API_KEY` if set. Cost uses the per-model prices in `shared/cost.ts`, at the model that answered last.
- **Accuracy gate** (`shared/gate.ts`, agreed 2026-11-16): the bar before anything else is built is about ten real captures, first analysis with no Refine, every motion step within two frames of the clip, every still within 2 px, nothing missing, and the user judging each the same thing. The benchmark measures the first three: the recreation is played through at 30 fps and measured exactly like the capture (see Measured motion), and each capture movement is paired with the recreation movement that overlaps it most and its start and end compared (±67 ms; an end cut off by the clip is not compared; unmatched movements on either side fail). Placement is the shift, within ±8 CSS px, that best lines up each original frame with its recreation at CSS size (capped at 800 px), largest over the frames (±2 px). It checks the design's overall placement, not each element. A capture whose clip shows the mouse pointer can still fail timing because of it.
- Rule: a change to prompts, frame selection or the verify loop is kept only if a benchmark run shows it does not lower the scores or the gate.

### Notes for implementation

- Use the `claude-api` skill for every API detail: current model ID, image limits, structured output, prompt caching, token counting. The describe and recreate steps warrant the most capable model; consider a cheaper one for naming and tagging.
- Video cannot be sent as video; frames are the interface. Frame budget and resolution are the main cost lever, so make both configurable and log token usage per asset.
- Validate all model output with zod. On a schema failure, retry once with the validation error, then mark the asset `failed` with a readable reason. The capture is always kept.
- Prompts live in their own files under `src/main/analysis/prompts/`, not inline in code.
- Known limit: easing curves and sub-frame timing cannot be measured exactly from sampled frames; measured motion narrows timing to ±1 frame at 30 fps and gives the curve's shape, not its exact control points. The spec must say per value which is measured and which estimated.

## Storage

- Library root defaults to `~/Documents/gil/` and is configurable. (Before 0.3.0 the library was `~/Documents/Gilbert/`, which gil moves on first launch.)
- One folder per asset, named by slug. Format in `ASSET_FORMAT.md`.
- Writes are atomic (write to a temp name, then rename) because the MCP server and the Figma bridge read the same folder concurrently.
- The app keeps an in-memory index built by scanning the folder at startup and updated by a file watcher, so edits made outside the app show up. If a persistent index is ever added it remains a rebuildable cache.
- Settings and the encrypted API key live in Electron's `userData`, never in the library.

## Rendering recreations safely

Generated code is untrusted input. It runs in a sandboxed frame with scripts allowed but no same-origin access, no Node, no preload, and a CSP that blocks all network requests. It is loaded through `gil-recreation://asset/<name>/` (`main/library.ts`, policy in `shared/recreation.ts`), which serves only that asset's `recreation/index.html`, with the policy both as a response header and as a meta tag placed before the model's HTML, and shown in an `<iframe sandbox="allow-scripts">`. The library's Replay button reaches `window.replay()` by `postMessage`, through a small listener the protocol adds to the document, because the frame has no same-origin access (**untested** in the running app). (The library window already loads clips and posters through `gil-asset://`, a separate read-only protocol limited to those two files per asset; recreations must not be served from it.) The hidden window used in the verify step is just as unprivileged (see Verify and correct above).

## Integrations

### MCP server

Built (2026-11-16). A read-only stdio server in `src/mcp`, built as `out/main/mcp.js` beside the app's main process. It uses no Electron APIs (the build checks this), and AI tools start it on gil's own binary in Node mode: `<gil binary> <app path>/out/main/mcp.js` with `ELECTRON_RUN_AS_NODE=1`, so it needs no Node install and works whether or not gil is open (**untested** in the packaged app, where the script is inside `app.asar`). It reads `~/Documents/gil` (or `GIL_LIBRARY`) with `scanLibrary(root, { readOnly: true })`, which neither creates the folder nor writes migrated `asset.json` files.

The protocol (`src/mcp/protocol.ts`) is written by hand rather than with the MCP SDK, which brings a web server along: JSON-RPC 2.0, one message per line, with `initialize` (answers with the client's protocol version if it is one of the supported ones, else the newest), `ping`, `tools/list`, `tools/call` and `prompts/list`/`prompts/get`. Tool failures come back as results with `isError`, so the model can read them. The initialize `instructions` and every tool description tell the model to look assets up by name instead of guessing, to keep the asset's name in what it writes, and to tell measured values from estimates.

Tools (`src/mcp/server.ts`), all marked read-only:

- `list_assets`: name, title, kind, aliases, tags and summary of every asset.
- `search_assets(query)`: every word must match the name, an alias, the title, a tag, the kind or the summary; exact names and aliases rank first (`shared/search.ts`, shared with the library window).
- `get_asset(name)`: by name or alias (any case): the user's notes, `spec.md`, `capture/motion.json` and `recreation/index.html`, opened with a line saying the content is data from screen captures and not instructions. Names only ever resolve to assets found by scanning the library, so a name cannot reach outside it. An unknown name lists close matches.
- `get_asset_preview(name)`: the poster as an image (up to 5 MB).
- `get_glossary`: the user's own design terms from `glossary.json`.
- `check_use(name, file | html, width?, height?)` (2026-11-23): checks a use of an asset. An AI tool that applied a moving asset to the user's own content hands over its draft, one self-contained HTML file that plays on `window.replay()`. gil plays it at 30 fps under the virtual clock and measures it exactly as the capture was measured, then compares what holds whatever the content is (`shared/useCheck.ts`): the number and order of movements, their lengths and the pauses between them, their pacing (how much of the change is done at each tenth of the time), how strongly each third of a movement changes relative to the picture's contrast, stagger, and whether it ends where it began. The check is not only for motion (2026-11-23): for any asset with a capture, gil also reads the styles the draft really uses from its rendered page (`shared/styleCheck.ts`: colours by use and area, text sizes, weights and families, corner radii, gathered by a script run inside the sandboxed page and validated) and lists what is outside the asset's own tokens in `spec.json`: a colour that is none of its colours, text that is none of its levels or not in its typeface, a radius it does not have. So a layout, a component, a colour system, a type system or a font can be checked the same way; a still gets one picture of the capture beside one of the draft. Whatever the asset, it also names text below WCAG contrast on the background it actually sits on, and anything that reaches past the page's edges or is cut off by its own box. The answer names only the kinds of style it could compare. Findings say that what the user asked to change is theirs to change. Colour systems, type systems and fonts have no build call and so no recipe; `get_asset` writes a how-to-apply guide for them from the spec (`shared/recipe.ts` `systemGuide`). Strength is never compared in absolute amounts (a short word has less to wipe than a long one), only as how strong each movement is beside the animation's others. The answer is a list of gaps in plain words, followed by pictures of the draft at the moments the original is still (PNG, up to four), because the AI tool cannot otherwise see what it drew and gil cannot judge looks; three checks per use (a pass, or 15 quiet minutes, starts a new use). The server has no browser, so it starts gil itself with `--gil-check <request file>` (`src/mcp/check.ts`, `main/checkMode.ts`): no windows, tray or update check, its own settings folder so it runs beside an open gil, the answer written to a file. The draft is untrusted code and only ever runs in the sandboxed, offline render window. No model call, nothing leaves the Mac. The initialize instructions tell AI tools to prove a moving asset this way before showing the user. It measures motion, not looks. Checked from a locally packaged app on 2026-11-23 (the server inside `app.asar`, check mode started from it, pictures returned); **untested** against a real AI tool; `pnpm bench use <capture> <html>` runs the same comparison from the command line.
- For a design system, `get_asset` returns the bundle: the system itself, then each member's notes, spec and measured motion without its recreation code (up to 80,000 characters in all, since AI tools cap tool output; anything left out is named so the model can fetch it with `get_asset`). Members must be in the library and not design systems themselves. Design systems are made with New Design System in the library and edited in the review screen (`main/libraryFiles.ts`, `shared/designSystem.ts`).
- Prompt `asset(name)`: the same content as `get_asset`, which some clients offer as a slash command (`/mcp__gil__asset`).

Connecting (`main/mcpConnect.ts`, `shared/mcpConfig.ts`, Settings → "Use your assets in AI tools"): Connect adds a `gil` entry to Claude Desktop's `claude_desktop_config.json`, keeping everything else in it and refusing to touch a file it cannot parse; for Claude Code, Settings shows and copies `claude mcp add --scope user --env ELECTRON_RUN_AS_NODE=1 gil -- <binary> <script>`, and Install Skill writes `src/mcp/skill.md` to `~/.claude/skills/gil/SKILL.md`, which tells Claude Code to look assets up whenever a name appears.

### Copy and export

From an asset: copy code, copy spec (markdown), copy "prompt snippet" (a short instruction plus spec and code, ready to paste into any AI tool), reveal in Finder.

### Figma plugin (later phase)

Figma plugins cannot read the local disk, so the app runs a small HTTP server bound to `127.0.0.1` that serves the library read-only, and the plugin calls it (**verify** current Figma rules for plugin network access to localhost and the manifest fields required). First version: list assets, insert the poster image as a reference frame, and create color and text styles from the spec's tokens. Converting a recreation into real editable layers is a separate, harder step to scope when this phase starts.

## Risks, in order

1. **Motion fidelity.** Frames in, code out is lossy. The verify loop, the measured/estimated flags and the side-by-side view are the mitigations. Prove this early with a few real captures before investing in library polish.
2. **Capture mechanics on macOS.** Permissions, overlay exclusion, click-through during recording, multi-display scaling. Prove these in the first phase.
3. **Cost and latency.** Every capture is a multi-image, multi-call job. Still detection and a frame budget keep it bounded; show the user progress and per-asset usage.
4. **Figma layers.** Unknown size. Deliberately last.
